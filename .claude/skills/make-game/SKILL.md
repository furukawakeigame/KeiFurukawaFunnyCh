# ゲームを作ってサイトに公開する

ユーザーとは日本語でやり取りする。引数: $ARGUMENTS

このスキルは Codex とも共有している。リポジトリ直下の `AGENTS.md` から Codex がこのファイルを読むので、手順を変えたときは `AGENTS.md` の「Codex で作業するときの読み替え」も合っているか確認する。

各フェーズの終わりでユーザーに確認し、OKが出てから次へ進む。どのフェーズにいるかを毎回はっきり伝える。
すでに完成したゲーム（ファイルやフォルダのパス）を渡された場合は、1〜2を飛ばし、「3. 実装」の配置の手順から始める。

## 1. 企画

アイデアを一緒に膨らませ、短くまとめる。

- どんなゲームか（ひとことで）
- 何が面白いのか（遊びの核）
- 操作方法（PCのキーボード／マウス、スマホのタッチ）
- 1回あたりのプレイ時間の目安

アイデアがない場合は、3つほど案を出して選んでもらう。最初の作品は**小さく作れるもの**を勧める。

## 2. 仕様

企画をもとに、作るものを具体的に決める。チャット上に箇条書きで示し、OKをもらう。

- **フォルダ名**: 半角英小文字・数字・ハイフンだけ（例: `jump-cat`）。URLになる。`games/` に同じ名前がないか確認する。
- **タイトル**と、一覧に出す**1行の説明文**（一覧には今はタイトルだけが出る）
  - タイトルは**8文字以内**にする。トップページは3列表示で、タイトルを改行せず画面幅に合わせて縮めているため、9文字以上だとスマホでカードからはみ出す危険がある。9文字以上にしたいときは、トップページの `style.css` の調整が必要なことをユーザーに伝える。
- 画面の流れ（タイトル → プレイ → 結果 → もう一度）
- ルール（勝ち負け・スコア・ゲームオーバーの条件）
- 操作（キーボード／マウスとタッチの両方）
- 見た目・音の方針（素材は自作か、コードで描く図形を基本にする）

## 3. 実装

`games/<フォルダ名>/index.html` に作る。

- 基本は**1ファイル**にまとめる（HTML＋`<style>`＋`<script>`）。ビルドは使わない。ライブラリは必要なら使ってよい（3Dなら three.js など）。npm は使わず、無料のCDN（jsdelivr など）からバージョンを固定して読み込む（例: `<script type="importmap">{ "imports": { "three": "https://cdn.jsdelivr.net/npm/three@0.160.0/build/three.module.js" } }</script>`）。CDNが読めないときに画面へ一言出すようにしておく。画像や音を使う場合も同じフォルダに置き、**相対パス**で読み込む。
- **デザインの方針**:
  - 画面上の**文字や数字は極力入れず**、見ただけで伝わるようにする。遊び方の説明文は置かず、見れば分かる操作にする（説明が要るなら絵や動きで伝える）。進み具合や結果も、できるだけ数値ではなくゲージ・色・絵の変化などで見せる。企画の段階からこの方針で考える。
  - **シンプルで分かりやすいレイアウト**にする。要素を詰め込まず、遊ぶのに必要なもの（ゲーム画面・操作ボタン・結果）だけを置く。
  - **絵文字は使わない**（AIっぽく見えるため）。ボタン・結果・X投稿文・アイコン代わりの記号も含めて使わず、文字か、SVG／Canvas で描いた図形にする（音ボタンのスピーカーも SVG で描く）。
- 必ず入れるもの:
  - `<meta charset="UTF-8">` と `<meta name="viewport" content="width=device-width, initial-scale=1">`
  - トップに戻るリンク `<a href="../../">← トップへ戻る</a>`
  - PCとスマホの両方で遊べる操作。タッチ操作中に画面がスクロールしないようにする。
  - **画面比率とウィンドウサイズへの対応**（毎回必ずやる）: 縦長スマホ・横向きスマホ・タブレット・大きいPC画面・横に広く背の低いウィンドウのどれでも、遊ぶのに必要なもの（キャラ・操作する物・ゴールなど）がはみ出さず、小さくなりすぎず、余白ばかりにならないようにする。
    - 「横幅で決まる大きさ」と「高さで決まる大きさ」の小さい方を使って、必要な範囲が必ず入るようにする。極端に大きくならないよう上限も付ける。
    - 余った高さ（縦長スマホなど）は、空や背景に回して絵を画面の真ん中あたりに置く。地面や下の余白だけが広がらないようにする。
    - 上のヘッダー（戻るリンク・音・言語）と下の 80px の空白には、大事な物を置かない。
    - 結果パネルなどの重ねて出す画面は、見せ場（倒れた猫など）にかぶらない位置に出す。背の低い横長画面では、横に並べる（`@media (max-height: 520px) and (min-aspect-ratio: 4/3)` など）。
    - 文字やボタンは `clamp()` などで画面に合わせて大きさを変え、大きい画面で小さく見えすぎないようにする。
    - プレイ中にウィンドウの大きさや画面の向きが変わっても、その場で描き直して崩れないようにする（`resize` で配置を計算し直す）。
  - **言語の切り替え（日本語・韓国語・英語・タイ語）**: 文言（トップへ戻るリンク・ボタン・結果の文・X投稿文・ページタイトル・ゲーム内の言葉も）をすべて4言語の辞書にまとめ、音ボタンの横に `<select>` を置いて「日本語 → 한국어 → English → ไทย」の順で並べる。**最初の言語は遊ぶ人に合わせて自動で決める**: `navigator.languages`（端末・ブラウザの言語設定の優先順）を上から見て、最初に対応している言語を選び、どれにも当たらなければ英語にする。自分で選び直したときだけ `localStorage` に保存し、次からはそれを使う。結果画面を表示中に切り替えても、その場で文言が変わるようにする（焼きそばパンゲームの実装を参考にする）。タイ語は修飾語が後ろに来るなど語順が違うので、言葉を組み合わせる文は言語ごとに組み立てる。X投稿のハッシュタグはどの言語でも同じ日本語のものにする。
  - **画面の下に 80px ほどの空白**を入れる（`padding-bottom: calc(80px + env(safe-area-inset-bottom))` など）。Xのアプリ内ブラウザで開くと、下部にXの投稿文が重なってボタンが隠れるため。結果パネルなどの重ねて出す画面も同じ。
  - アイコン `games/<フォルダ名>/icon.png`（正方形のPNG、512×512 推奨）。トップページの一覧に表示する。ユーザーが用意していなければ、ゲームの絵を使って Canvas で描くなどして作り、見せてOKをもらう。ゲームのページにも `<link rel="icon" href="icon.png">` と `<link rel="apple-touch-icon" href="icon.png">` を入れる。
  - `<head>` の先頭（`<head>` の直後）に、トップページと同じ Google アナリティクスのタグ（`G-9E13VFBMWN`）をそのままコピーして入れる。
  - X などにURLを貼ったときにアイコンとタイトルが出るよう、`<head>` にカード用の meta タグを入れる。`og:url` と `og:image` だけは相対パスでは読まれないので、公開URLを `https://` から書く。カードはタイトルとアイコンだけにし、**説明文（`description` / `og:description`）は入れない**。

    ```html
    <meta property="og:type" content="website">
    <meta property="og:site_name" content="ふるかわけい面白チャンネル">
    <meta property="og:title" content="タイトル">
    <meta property="og:url" content="https://keifurukawafunnych.com/games/<フォルダ名>/">
    <meta property="og:image" content="https://keifurukawafunnych.com/games/<フォルダ名>/icon.png">
    <meta name="twitter:card" content="summary">
    ```

    大きい画像のカードにしたいと言われたら、1200×630 の `ogp.jpg`（タイトル・ひとこと説明・ゲームの絵）を作って同じフォルダに置き、`og:image` を `ogp.jpg` に、`twitter:card` を `summary_large_image` にして、`og:image:width`（1200）と `og:image:height`（630）も足す。画像はゲームのページ上で Canvas に描いて書き出すと、ゲームと同じ素材で作れる。
- **固まらないようにする**: 3Dなどで重い準備（形の生成・シェーダーのコンパイル・動画づくり）は、結果が出た瞬間にまとめてやらない。結果が決まった時点（最後のボタンを押した時など）から少しずつ進め（`setTimeout` で区切る）、使う質感は待ち時間に `renderer.compileAsync` で先に用意しておく。動画は別の renderer を作らず、表示の合間に1コマずつ描く（焼きそばパンゲームの実装を参考にする）。
- **最初の1回だけ重くならないようにする**（毎回起きやすい）: 初回の操作や初回の衝突で一瞬カクつくのを防ぐ。
  - 音: `AudioContext` は最初の効果音の時に作らず、最初の `pointerdown` で作り、音量0の音を一度鳴らして準備しておく。
  - 毎フレーム `document.body.style` などDOMのスタイルを書き換えない（値が変わった時だけ書く）。
  - 物理エンジンや描画は、読み込み時に1回空回し（`Engine.update` と描画を1回）しておく。
  - フレーム間の時間は上限を付けて（例: 50ms）、最初のフレームでまとめて計算しないようにする。
- **フレームレートに左右されないようにする**: 60Hz・120Hz・144Hz の画面や、重くて 30fps に落ちた端末でも、同じ速さ・同じ難しさで動くようにする。
  - 物理や移動は「1フレームにいくつ進む」で書かず、固定の時間刻み（例: 1/60秒）で計算する。`requestAnimationFrame` の経過時間をためておき、その分だけ刻みを回す。
  - 高Hzの画面でカクつかないよう、描画は直前の2つの刻みの間を補間する。
  - 演出のタイマー（エフェクトの消える時間など）も、フレーム数ではなく経過時間で進める。
- 文言の約束: 重さ・点数などの数値には単位を付ける（例: 「250g」）。結果画面に、結果に応じた一言コメント（「なかなかの腰つき」など）は入れない。結果は数値などだけで見せる。
- X投稿の文には、必ず**ハッシュタグ「#<タイトル>ゲーム」**（例: `#焼きそばパンゲーム`）と**ゲームのURL**を入れる。英語表示のときも同じハッシュタグにする。URLは intent の `url=` に、Web Share で共有するときは本文の末尾に入れる。
- X投稿ボタンは `https://x.com/intent/post?text=…&url=…` への**本物の `<a>` リンク**にする。スマホでは `target` を付けず同じタブで開く（`window.open` で新しいタブを開くと X アプリに切り替わらない）。PC（`(pointer: coarse)` でないとき）は `target="_blank" rel="noopener"` で開く。
- **X投稿には必ず結果画像を付ける**（頼まれなくても毎回入れる。振り子倒立・巨大ヤギの実装を参考にする）:
  - 結果が出た瞬間のゲーム画面を 1080×1080 の Canvas に切り抜き（倒れた猫などの見せ場が枠に入るように位置を決める）、結果の数値（単位つき）を大きく、ゲームのタイトルを小さく重ねる。
  - スマホは Web Share API（`navigator.share({ files, text })`）で画像ごと共有シートに渡す。本文の末尾にゲームのURLを入れる。PCは画像を保存（ダウンロード）してから `https://x.com/intent/post` を開く。
  - 共有用の画像ファイル（`File`）は、結果が出た時点と言語を切り替えた時点で先に作っておく（クリック時に作るのを待つと Safari で共有が止まるため）。
  - Webの投稿URLでは画像を添付できないこと（PCでは保存した画像を自分で添付する）をユーザーに説明しておく。
- 頼まれたら追加する機能（麻辣湯チャレンジで作った実装を参考にする）:
  - **X投稿ボタン（結果の動画つき）**: 焼きそばパンゲームの実装を参考にする。結果が出たら裏で、もう1つの WebGLRenderer で1フレームずつ描き、WebCodecs（H.264）＋`mp4-muxer` で MP4 にしておく（クリック時に待つと Safari で共有が止まるため）。回転などの動きは時間でなくフレーム番号で決め、最後のフレームの次が最初のフレームにつながるようにして、きれいにループさせる。スマホは**押したら必ず共有メニューを開く**（`navigator.share` があれば常に使い、動画ができていれば動画つき、まだなら文とURLだけ。失敗しても x.com には飛ばさない）。PCは動画を保存してから投稿画面を開く。注意点としてユーザーに伝えること: 結果が出た直後（動画ができる前）に押すと動画なしで共有される（その間はボタンを薄く表示する）。Xアプリ内のブラウザは共有メニュー自体が使えないことが多く、押しても何も起きない場合がある（ゲーム側では直せない。必要ならブラウザで開くよう案内を出す）。`VideoEncoder` は https でしか使えない。
  - **自分の画像を具材などに追加**: `<input type="file">` で読み込み、縮小して `localStorage` に保存する（サーバー不要）。
- 既存ゲームを持ち込む場合: 中身を `games/<フォルダ名>/` にコピーし、入口を `index.html` にする。上の「必ず入れるもの」が足りなければ追加し、`/` で始まるパスや `C:\...` のパスは相対パスに直す。ゲームの中身は、頼まれない限り変えない。

## 4. 確認

- このPCには Python がないので、ローカルサーバーは `.claude/serve.ps1`（PowerShell製）を使う。`.claude/launch.json` の `site` 設定で、ブラウザペインから起動できる（`preview_start` に `name: "site"`）。
- ブラウザペインで `http://localhost:8000/games/<フォルダ名>/` を開き、コンソールエラーがないことを確かめる。
- **画面サイズの確認**: スマホ縦（320×568・375×667・390×844）、スマホ横（844×390・640×360）、タブレット（768×1024）、PC（1280×800・1920×1080）、背の低い横長ウィンドウ（1280×450）で、プレイ画面と結果画面の両方を見る。横あふれがないこと、遊ぶのに必要なものが画面に収まって小さすぎないこと、結果画面や吹き出しが見せ場やボタンに重ならないこと、ボタンが画面に収まることを確かめる。確認が終わったら表示サイズをデスクトップに戻す。
- **テストプレイ用URL**: ユーザーがスマホなどで遊べるよう、公開前のゲームを非公開の Artifact として出し、リンクを渡す（毎回やる）。
  - `games/<フォルダ名>/index.html` をスクラッチパッドにコピーし、`<!DOCTYPE>`・`<html>`・`<head>`・`<body>` のタグと、charset・viewport・`icon.png` を参照する行を消してから、Artifact ツールで publish する（`icon` は `game`）。CDNは jsdelivr なら読める。
  - 修正したら同じコピーを作り直して同じパスで publish すると、同じURLのまま更新される。
  - Artifact では `../../` のリンク、ダウンロード、Web Share は動かないので、そこは本番で確かめる。
- ユーザーにも遊んでもらい、感想や直したい点を聞く。直したい点があれば修正し、OKが出るまで繰り返す。
- 実機でしか確かめられないこと（タッチ操作、共有シート、ファイル選択など）は、確認できていないと正直に伝える。

## 5. デプロイ

1. `index.html` の `<ul class="games">` の**先頭**に、新しいゲームを**アイコン付き**で、既存の `<li>` と同じ形で追加する。`icon.png` がまだなければ、先に用意する（「3. 実装」を参照）。

   ```html
   <li>
     <a class="icon" href="games/<フォルダ名>/"><img src="games/<フォルダ名>/icon.png" alt="" width="72" height="72"></a>
     <div>
       <a href="games/<フォルダ名>/">タイトル</a>
       <p>説明文</p>
     </div>
   </li>
   ```

2. 追加・変更したファイルだけを `git add` し、`Add game: <タイトル>` というメッセージでコミットする。
3. 公開のタイミングをユーザーに確認する。
   - **すぐ公開**: `git push` する。数分でサイトに反映されることを伝え、URLを案内する。
   - **時刻を指定して公開**（X投稿の時刻に合わせたいときなど）: 下の「予約公開」を使う。
4. URLの案内:
   - ゲーム: `https://keifurukawafunnych.com/games/<フォルダ名>/`
   - トップ: `https://keifurukawafunnych.com/`

### 予約公開（GitHub Actions）

PCやアプリを閉じていても動くよう、GitHub Actions で公開する。

1. ゲームのコミットを公開用ブランチ `publish-<フォルダ名>` に置き、`main` は `origin/main` に戻す。
2. `main` に下のワークフローだけをコミットして push する（ゲームはまだ公開されない）。その後、公開用ブランチを `main` の上に rebase して push する。
3. GitHub の時刻指定実行は 10〜30 分以上遅れることがあるので、**X投稿の1時間45分前**くらいに設定する。`:00` や `:15` などきりの良い分は混むので避ける（例: 19:00 投稿なら 17:13 JST → `13 8 ...`）。cron は UTC（日本時間 − 9 時間）。
4. 公開までの修正は**公開用ブランチにコミット**する。`main` に直接コミットすると、取り込み（fast-forward）が失敗する。
5. ユーザーに伝えること: 予定時刻の40分後に「Actions」タブで緑のチェックを確認する。動いていなければ「Run workflow」で手動実行できる。公開前にXでリンクを貼って試すと、カードなしの状態が記憶されることがあるので避ける。

```yaml
name: Publish <タイトル>
on:
  schedule:
    - cron: '<分> <時(UTC)> <日> <月> *'
  workflow_dispatch:
permissions:
  contents: write
jobs:
  publish:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
        with:
          ref: main
          fetch-depth: 0
      - name: Merge publish branch into main
        id: merge
        run: |
          if ! git ls-remote --exit-code origin publish-<フォルダ名> >/dev/null; then
            echo "already published"; exit 0
          fi
          git fetch origin publish-<フォルダ名>
          git merge --ff-only origin/publish-<フォルダ名>
          git push origin main
          git push origin --delete publish-<フォルダ名>
          echo "published=true" >> "$GITHUB_OUTPUT"
      - name: Wait until the game page is live
        if: steps.merge.outputs.published == 'true'
        run: |
          for i in $(seq 1 30); do
            curl -fsSL https://keifurukawafunnych.com/games/<フォルダ名>/ >/dev/null && exit 0
            sleep 20
          done
          exit 1
```

## 6. X告知

ユーザーは @furukawakeigame で、プレイ動画つきの投稿で告知する。

1. **動画**: 9:16 の縦長（1080×1920）で、**プレイ映像だけ**にする。字幕・タイトル画面・エンドカードは入れない。最後にゲーム内の**オチ**（失敗して怒られる、など）があるとよい。どんなオチにするかはユーザーに確認する。
2. **撮り方**: 次の2通り。ユーザーに「自分で遊んで撮るか、自動で撮るか」を確認する。
   - **自分で遊んで撮る（録画ツール）**: `.claude/recorder.html` を使う。ゲームごとの書き換えは不要。
     - 開き方: 公開後は `https://keifurukawafunnych.com/.claude/recorder.html?game=<フォルダ名>`。公開前はローカルサーバーで `http://localhost:8000/.claude/recorder.html?game=<フォルダ名>`。**PCの Chrome か Edge** で開く（スマホ・Safari・Firefox は不可）。
     - 画面: 左に 9:16 の枠でゲームが入り、右に操作パネルがある。ゲームの選択肢はトップページの一覧から自動で読む（`?game=` で最初に選ぶゲームを指定）。
     - 手順: 「● 録画開始」→ 共有の画面で**「このタブ」**を選ぶ（音も録るときは「タブの音声も共有」をオン）→ 3・2・1 のあと録画開始 → 枠の中で遊ぶ → 「■ 停止して保存」→ その場で再生して確認 → 「MP4を保存」。
     - 仕組み: タブの画面共有（`getDisplayMedia`）を枠の部分だけ切り抜き（`CropTarget`、使えなければ位置から切り抜く）、WebCodecs で H.264／AAC にして `mp4-muxer` で 1080×1920・30fps の MP4 にする。枠の外のボタン・説明と、カウントダウンの数字は映らない。
     - 注意として伝えること: 録画中はウィンドウの大きさを変えない。音が録れない環境では映像だけになる（画面に表示される）。
   - **自動で撮る**: `record-template.html`（このスキルのフォルダ）を `.claude/record.html` にコピーし、そのゲーム用に書き換える。実際のゲームを iframe で自動操作し、画面を 1080×1920 の Canvas に描き直して MP4 にする。撮れたら通常再生で最後まで見て、オチまで映っているか確かめてから `.claude/out/` の動画をユーザーに渡す。`.claude/out/` はコミットしない。
3. **投稿**: ゲームのURLは本文ではなく**リプライ**に貼る（動画つきの投稿ではリンクカードが出ないため）。Xではリプライを予約できないので、投稿後に手動で貼ってもらう。
4. カードが出ないと言われたら、まず meta タグを確認し、問題がなければ時間をおくか URL に `?v=2` を付けて貼り直す。
